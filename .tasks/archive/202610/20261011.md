# 新增 project-rename 能力（目录改名与宿主状态迁移）

## 背景

项目目录改名后，各 IDE / 工具中「跟随目录名」的关联状态（工作区存储、打开历史、缓存、worktree 占位等）会与实际路径失配，表现为工作区状态丢失、缓存错乱、最近打开异常。该类需求高频且重复，值得沉淀为 opsbox 的通用能力。

本仓自身即为首个用例：工作区目录名为随手取名，与包名 `@fxri/opsbox` 不一致，需借本能力完成目录改名与状态迁移。

## 取证事实（本机实测）

目标宿主采用 VS Code 系数据布局，数据根分两处（均可经环境变量在运行期推导，不写死）：

| 位置 | 内容 | 说明 |
| --- | --- | --- |
| `<宿主应用数据根>/User/` | `workspaceStorage/<id>/`（`workspace.json` + `state.vscdb`）、`History/<id>/entries.json`、`globalStorage/`（`storage.json` + `state.vscdb`） | VS Code 系标准布局 |
| `<宿主用户数据根>/` | `worktrees/<项目目录名>/`（空占位）、`hub_event_cache/` | 该宿主特有 |

- `workspaceStorage` / `History` 的目录名 `<id>` **不可由工作区路径推算**：实测对 6 种 URI 形式做 MD5 均不匹配，累计穷举约 150 个候选零命中；且观测到两个不同 id 指向同一 folder ⇒ id 非 URI 纯函数
- 因此「新 id」只能由宿主自身在下次打开时生成 ⇒ 二进制状态（`state.vscdb`）迁移必须分两趟完成

## 实施方案

### 能力设计（对标 `mysql-recover` 既有范式）

- 能力名 `project-rename`：描述用户目标、宿主无关（符合 C-3）
- 宿主差异经适配层隔离，VS Code 系（Trae / VS Code / Cursor / Windsurf / VSCodium 布局同构）共用一个参数化适配器 + 变体表
- 目录结构：
  - `src/project-rename/{index,command,engine,plan,artifacts,paths}.ts`
  - `src/project-rename/adapters/{types,vscode-family,registry}.ts`
- 核心契约：
  - `HostAdapter`：`id` / `label` / `detect()` / `scan(oldPath, newPath)`
  - 载体三分类：文本（改写路径）／二进制不透明（整体搬迁或让宿主重生成，绝不解析改写）／缓存（丢弃）

### CLI

```
opsbox project-rename <old-path> <new-path>
  --dry-run         仅输出计划，不落盘
  --yes             跳过确认
  --host <ids>      限定宿主（默认全部检出）
  --backup-dir <d>  备份目录（默认 .opsbox/project-rename/<时间戳>/，符合 C-4）
  --no-backup       跳过备份（危险）
  --resume          执行第二趟（合并 state.vscdb）
```

### 迁移矩阵（Trae / VS Code 系）

| 位置 | 载体 | 动作 |
| --- | --- | --- |
| `<app>/User/workspaceStorage/<oldId>/workspace.json` | 文本 | 改写 folder URI → 新路径 |
| `<app>/User/workspaceStorage/<oldId>/state.vscdb` | 二进制 | 第一趟备份；第二趟整文件复制入宿主新生成的 `<newId>` |
| `<app>/User/History/<oldId>/entries.json` | 文本 | 改写 resource URI |
| `<app>/User/globalStorage/storage.json` | 文本 | 改写含旧 id 的键 |
| `<app>/User/globalStorage/state.vscdb` | 二进制 | 探针检测，含旧路径才整文件备份并复制回原位 |
| `<user>/worktrees/<旧目录名>/` | 目录 | 改名为新目录名 |
| `<user>/hub_event_cache/` | 缓存 | 丢弃 |

### 双趟流程

1. 第一趟（宿主全关）：dry-run → 备份 → 文本改写 + 目录改名 + 缓存丢弃；旧 `state.vscdb` 一并备份，旧 `<oldId>` 目录保留不动
2. 用户重开宿主打开新路径，再关闭（宿主据此生成 `<newId>` 目录）
3. 第二趟（`--resume`）：按新 URI 反查 `<newId>` → 把备份的旧 `state.vscdb` 整文件复制过去 → 清理旧 `<oldId>` 目录

二进制状态采用**整文件复制**：不解析、不改写 SQLite 内容（符合「二进制不透明载体」纪律）。代价仅为库内少数指向旧路径的键失效，由宿主自行容错重建；换来零新增依赖、零包体积增量、零构建复杂度。

- **Step 2**：以真实项目目录（含中文目录名）做端到端验收

## 扩展：Trae 会话关联状态迁移（20261011 补）

### 背景（以本仓实际改名验收发现）

以本仓自身改名（`ai-tool` → `opsbox`）验收时发现：宿主（Trae CN）自身的任务 / 会话记录未随目录迁移。只读取证确认：

- **会话 / 任务正文不可文件层迁移**：`globalStorage/state.vscdb` 的 `chat.ChatSessionStore.index` 为空、`draft:session:*` 仅输入框草稿；`%APPDATA%/Trae CN/ModularData/ai-agent/database.db` 体量约 1.2GB、非 SQLite、明文零命中（加密 / 私有格式）。会话与任务绑定「工作区身份」，正文不可文件层搬运。
- **可迁移的是项目关联引用**：`globalStorage/state.vscdb`（标准 SQLite `ItemTable(key, value)`）中 `solo-lite.local-project-folders`、`solo-lite.project-workspace-cache`、`vscode.github`、`terminal.history.entries.dirs` 等键仍含旧路径；改写后宿主有望把新路径识别为同一项目（实验性重关联）。
- **MCP 作用域目录残留**：`<用户数据根>/mcps/s_<目录名>-<8位hex>` 按项目路径命名，改名后旧目录残留、新目录由宿主重建；目录内容为宿主自动生成的 MCP 工具描述，无迁移价值，按「`s_<旧目录名>-<8位hex>` 全匹配即丢弃」处理（hash 规则对真实样本无法复现，亦无需复现）。

### 方案

# 恢复宝塔重装后遗留的旧 MySQL 库

## 背景

宝塔 Windows 面板重装后，MySQL 8.0.29 实例被重新初始化，`mysql.ibd`/`ibdata1`/`undo`/`redo` 等系统文件被覆盖，导致 MySQL 数据目录 `<data>` 下 9 个库目录里的 `.ibd`/`.MYD`/`.MYI` 成为"孤儿文件"：物理存在但数据字典无登记。`SHOW DATABASES` 仅返回 4 个系统库，旧库不可见。

全盘无 `mysql.ibd`/`ibdata1` 备份，旧数据字典已彻底丢失 → 整目录还原方案不可行，改走"重建字典条目 + 回填物理文件"路线。

待恢复 9 库（478 表：InnoDB 447 + MyISAM 31）：
`<db1>`、`<db2>`、`<db3>`、`<db4>`、`<db5>`、`<db6>`、`<db7>`、`<db8>`、`<db9>`

## 实施方案

统一 DDL 路线（不改 `my.ini`）：

- **InnoDB**：`CREATE TABLE`（重建字典）→ 运行中 `ALTER TABLE … DISCARD TABLESPACE` → 拷回旧 `.ibd` → 运行中 `ALTER TABLE … IMPORT TABLESPACE`
- **MyISAM**：`CREATE TABLE`（重建字典）→ 停机拷回 `.MYD/.MYI`（数据即文件，无需 IMPORT）

交付文件（本仓库根目录）：

- `sdi-to-ddl.mjs`：SDI→DDL 生成器（Node.js，环境无 Python）
  - InnoDB 用 `ibd2sdi.exe <x.ibd>` 取 stdout JSON 的 `type:1` 对象；MyISAM 直读库目录下的 `*.sdi` 的 `dd_object`
  - MyISAM 的 `.sdi` 文件名对长表名会截断，故改为遍历全部 `.sdi`、以内部 `dd_object.name` 反推 `.MYD/.MYI`
  - 跳过内部列与隐式索引；`collation_id`→字符集名（查 `information_schema.COLLATIONS`）
  - 产物：`ddl-out/manifest.json` + `ddl-out/ddl/<库>/<表>.sql`（478 份）+ `ddl-out/ddl/_databases.sql`
- `restore-old-dbs.ps1`：编排脚本（PowerShell 5.1，需管理员；含 DryRun）

阶段：

- Phase 0：停 MySQL → 整目录冷备（robocopy 到冷备目录 `<backup>`）→ 9 个孤儿库目录 move 到 staging → 起服务
- Phase 1：运行中建 9 库 → 逐表 `CREATE TABLE` → InnoDB 表 `DISCARD TABLESPACE`
- Phase 2：运行中从 staging 拷回 InnoDB 的 `.ibd`（`icacls /reset` 复位 ACL）→ 逐表 `IMPORT TABLESPACE`
- Phase 3：停服务 → 拷回 MyISAM 的 `.MYD/.MYI` → 起服务
- Phase 4：运行中校验（逐库表数、逐库体积、全量 `CHECK TABLE`、每库首表 `COUNT(*)` 抽样），报告落盘 `ddl-out/run-<时间戳>/restore-report.txt`

关键实现约束（已实测）：

- ⚠️ 孤儿 `.ibd` 会阻塞 `CREATE TABLE`，故 Phase 0 必须先整体挪出库目录
- ⚠️ MyISAM 与 InnoDB 字典注册统一走 DDL；`DISCARD TABLESPACE` 清空新建 InnoDB 表的数据文件后再导回，避免 schema mismatch

## 执行期根因修复

- ⚠️ **InnoDB 表名不能取 `.ibd` 文件名**：MySQL 8.0 对表名中不适合做文件名的字符做编码（`~`→`@007e`、`@`→`@0040`），含特殊字符的表其 `.ibd` 文件名 ≠ 真实表名，按文件名建表再导入会报 `ERROR 1812 Tablespace is missing`。`sdi-to-ddl.mjs` 的 `collectTables` 改为以 SDI 内 `dd_object.name` 为准；同步补齐 `main()` 调用点漏传的 `opts` 参数。修复后 `<table-a>`/`<table-b>` 两表名修正，478 表 / 告警 0。
- ⚠️ **`Invoke-MysqlQuery` 返回值被标量展开**：PowerShell 函数 `return (单行管线结果)` 会把单元素数组展开成标量字符串，调用处 `$rows[0]` 因此取到首字符（期望 5 取到 `'5'`，`[int]'5'`=53），导致 Phase 4 表数九处误报（53/49/50/51/49/54/49/50/49 恰为期望值首字符 ASCII 码）。修复为 `return ,@(...)` 强制数组返回，连带修正版本号显示被截断、抽样行数只显示首字符的问题。

## 影响范围

- 仅本机 MySQL 8.0.29 实例与其 datadir；不涉及其它盘数据
- 源目录先 staging 保护 + 整目录冷备 → 失败可完全回滚
- 不改 `my.ini` 配置

## 验证方式

- 逐库比对表数（与 SDI 提取结果一致）
- `CHECK TABLE` 通过、抽样 `SELECT COUNT(*)` 有数据
- 恢复后重建面板库记录（"从服务器获取"）并重建应用账号授权

## 回滚方案

`DROP DATABASE` 新建的 9 库 → staging/冷备目录移回原位 → 重启 MySQL，即回到当前状态。

## 风险

- ⚠️ `IMPORT TABLESPACE` 有 schema mismatch 风险，DDL 生成器须忠实还原列/索引/字符集/`ROW_FORMAT`；若 Phase 2 报错，须人工核对生成 DDL 与旧 `SDI` 的差异
- ⚠️ Phase 3 停机窗口内不可中断
- ⚠️ `@` 前缀临时表名需特殊引用
