# 全端通用规范（common）

> 归属：common（所有端适用）。条文全文见本节，索引见 index.md。

## C-1. 能力全平台

所有能力默认须跨平台（Linux / macOS / Windows）。

- **要求**：平台差异统一经适配层隔离，平台无关核心不得直接调用平台特有命令或路径；新增能力须同步给出各端适配实现；平台探测在运行期完成，不依赖编译期条件或用户手工指定。
- **反例**：平台无关核心直接调用 `systemctl` / `net` 等平台特有命令，或写死 `D:\...` 一类平台特有路径。
- **理由**：工具集面向跨平台用户，能力若绑定单一平台即丧失通用性；适配层隔离使平台无关逻辑可复用、平台差异局部化。
- **配套**：确不可跨平台者，须在能力文档显式声明支持的平台与降级范围。

## C-2. 真实信息零泄漏

任务区（`.tasks/`）与逻辑代码（`src/` 等）不得出现真实环境标识与凭据。

- **要求**：不得出现真实数据库 / 表 / 账号 / 口令 / 密钥 / token、真实主机名 / IP / 端口 / 域名 / 实例标识、机器特有的绝对路径与本地目录布局、生产数据样本、客户 / 项目 / 公司代号及其它可据以还原某台机器或某套环境的信息；需要真实输入时须参数化（`--data <dir>`）或占位（`<db>`），运行期从环境推导、不写死。
- **反例**：在任务档或代码中写死生产库表名、口令或客户代号。
- **理由**：真实信息入库会导致凭据泄漏与主体可定位，脱敏是任务区与代码可对外复用的前提。
- **配套**：厂商文档化的通用约定（如 Linux 宝塔 `/www/server`、Homebrew `/usr/local/opt`）与协议固定值（如 `127.0.0.1` / `root` / `mysql`）属允许项；范围限于任务区与逻辑代码，`package.json` / `LICENSE` 等元数据文件不在此列；归档块原则上不可变，确需脱敏更正时原位改写并在块内留痕。

## C-3. 能力维度组织

能力（capability）目录按「做什么」切分，不按宿主 / 工具 / 平台切分。

- **要求**：目录名即能力名（如 `mysql-recover`），描述用户目标，不得以宝塔 / trae 等宿主或工具命名；能力跨宿主可复用时须保持宿主无关；新增宿主支持时只扩适配层、不新增能力目录。
- **反例**：以宿主或工具名建目录（如 `baota/`、`trae/`），而非按用户目标命名。
- **理由**：按「做什么」组织使能力可跨宿主复用，宿主差异收敛于适配层。
- **配套**：宿主 / 平台差异经适配层隔离，见 `C-1`。

## C-4. 自定运行期产物收口

本工具自定的运行期产物统一落项目根下的隐藏目录 `.opsbox/`（以工具名命名，对标 `.terraform/` / `.turbo/` 等惯例）。

- **要求**：落点由命令默认值给出，可经选项（如 `--out` / `--work`）覆盖，不得默认散落于项目根；`.opsbox/` 属可确定性重生成的运行期产物，须按 `.gitignore` 排除、不入库。
- **反例**：运行期产物默认散落在项目根（如 `./tmp`、`./output`），或不加忽略误入库。
- **理由**：自定产物收口到工具专属目录，避免污染项目根，便于统一忽略与清理。
- **配套**：Node 生态标准产物（`node_modules/` / `dist/` / `coverage/`）受生态约定约束，保持根目录默认位置，不强行收口。

## C-5. 对外内容限本仓产品域

面向用户的对外内容（文档站页面与导航、README 等）只承载本仓产品域的内容。

- **要求**：镜像同源姊妹项目（如 `@fxri/toolkit`）时须甄别——通用工程基础设施（CI、CHANGELOG、文档站骨架等）可搬，对方的产品内容（AI 协作规则、提交信息规则、任务流程等）不得镜像为本仓产品内容。
- **反例**：把姊妹项目的 AI 协作规则、提交信息规则页直接搬进本仓文档站导航。
- **理由**：对外页面须回答「本仓这个工具怎么用」，镜像对方产品内容会导致领域错位、误导用户。
- **配套**：本仓自有的开发域资产（`AGENTS.md` / `.trae/rules/` / `.tasks/` 等）不受此限，其本就服务本仓开发者、不面向产品用户。

## C-6. 任务区不出现参考仓库名

`.tasks/` 内文本（任务档正文、归档叙述、frontmatter 字段值）指称外部仓库时，一律用**通用措辞**（如「接入方仓库」「被参考仓库」「姊妹仓」），不得写实名。

- **要求**：书写任务区文本前，凡需提及本仓以外的仓库，一律改用通用称谓；做技术验证 / 对照参考时同样只写「被参考仓库」这类泛称，不列被参考对象的实名清单。判据取「**是否以具体名称指涉某个外部仓库**」，与 `C-2` 的脱敏判据正交（本条管外仓指称、`C-2` 管环境标识与凭据）；依赖包名（如 `@fxri/toolkit`）、被调接口名与命令名等属本仓事实者照写。
- **反例**：在任务档正文或归档叙述里列举被参考仓库的实名（如「已把 `foo-web`、`bar-service` 的规范升级至最新版」），或把实名当作 frontmatter 字段的示例值——本仓文本随 git 分发后即携带外部仓库的目录命名，而读者只具本仓视角、无从判断该名与本仓的关系。
- **理由**：任务区是仓库自述面，只承载本仓事实；实名指涉外仓既污染本仓文本，又把某次会话偶发的参照对象固化成仓库事实，还随分发外泄无关仓库信息。
- **配套**：与研发流程「跨仓库改动各自归档」配套——后者管「记不记他仓的事」（视角），本条管「写不写他仓的名」（用词），两者同属任务区文本治理，互为补充。
